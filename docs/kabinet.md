# Личный кабинет Argus

Главное правило: **зашли — и сразу видно, что плохо, а что хорошо.**

## Экраны

| Экран | Что на нём | API |
|---|---|---|
| Вход | E-mail + пароль или Telegram (initData). Регистрация = подключение первого сайта. | — |
| Мои сайты | Сводка (сайтов / нужны действия / 152-ФЗ / всё хорошо) и карточки сайтов со статусом и шкалой риска. | `GET /api/sites` |
| Добавить сайт | Домен → строка датчика → обучение → проверка эталона → наблюдение. | `POST /api/sites/:id/mode` |
| Сайт · Обзор | Риск во времени, последние находки, режим. | `GET /api/sites/:id/summary` |
| Сайт · Изменения | «Было / стало», цепочка `скрипт → действие → получатель`, кнопки решения. | `GET …/changes`, `POST …/decision` |
| Сайт · Эталон | Что Argus считает нормой: скрипты с хешами, получатели, кто какие поля читает. | `GET …/summary` |
| Сайт · Сессии | Посещения и сырые события для разбора. | `GET …/sessions`, `…/events` |
| Сайт · Настройки | Привязка Telegram, сброс эталона, переобучение. | `POST …/tg-link`, `…/reset` |

«Мои сайты» и «Добавить сайт» — `site/cabinet.html`; экраны сайта (обзор, изменения, 152-ФЗ, эталон, журнал, подключение, датчик) — пульт `site/dashboard.html?site=…`.

## Статусы сайта

| Статус | Цвет | Когда |
|---|---|---|
| Нужны действия | красный | есть изменение с риском ≥ 0,6 (вторжение) |
| 152-ФЗ | фиолетовый | ПДн уходят за рубеж или к иностранному ресурсу |
| Проверьте | жёлтый | новое, но ниже порога (0,35–0,6) — ждёт подтверждения |
| Всё хорошо ✓ | серебро | отклонений нет |
| Обучение | лаванда | эталон ещё собирается, тревог нет |

## Решения владельца

- **Это мы — принять в эталон** — изменение становится нормой (новая версия эталона).
- **Это атака — инцидент** — открывается инцидент, изменение в эталон не попадает.
- **Скрыть** — убрать из списка без решения.
- Правовые находки (152-ФЗ) в эталон **не принимаются** — только «Оформлено» (например, после смены счётчика или уведомления РКН).

## Открытый вопрос: как выделить эталон у клиента

На стенде всё просто: сайт заведомо чистый, обучаемся и включаем наблюдение. У реального клиента три проблемы:

1. **Сайт может быть уже заражён** в момент подключения — тогда скиммер попадёт в «норму».
2. **Сайт меняется** — маркетолог добавил виджет, обновился плагин.
3. **Страницы разные** — на главной одни скрипты, на оплате другие.

### Черновик решения: эталон из трёх источников

| Источник | Что даёт |
|---|---|
| **Наблюдение** (обучение) | Факты: какие скрипты, хеши, получатели, кто читает поля. Собирается по типам страниц (шаблон URL: `/product/*`, `/checkout`). |
| **Политика** (справочник) | Работает с первой секунды: передача ПДн за рубеж, чтение поля «карта» чужим скриптом, известные вредоносные домены подсвечиваются **даже во время обучения** — обучение не «отмывает» нарушение. |
| **Подтверждение владельца** | После обучения кабинет показывает инвентаризацию: «нашли 7 скриптов и 4 получателя — это всё ваше?». Неподтверждённое в эталон не попадает. |

**Когда обучение закончено** — не по таймеру, а по двум условиям:
- *стабилизация* — за последние K посещений не появилось ни одного нового элемента;
- *покрытие* — каждая ключевая страница (особенно с формами) посещена не меньше M раз.

Если трафика мало — эталон можно дополнить **синтетическим прогоном**: сервер сам открывает страницы
в headless-браузере. Это заодно второй канал наблюдения (если злоумышленник вырежет датчик).

**Эталон версионируется:** каждое «Это мы — принять» — новая версия с датой и автором. Можно откатиться
и видно, кто и когда принял изменение. При редизайне — кнопка «Переобучить».

Вопросы для обсуждения с руководителем: значения K и M (калибровка на расширенном эксперименте),
нужен ли эталон по типам страниц уже в прототипе, достаточно ли инвентаризации владельцем как защиты от «заражённого старта».
