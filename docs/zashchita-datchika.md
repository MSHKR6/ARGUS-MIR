# Защита датчика от отключения

## Главная мысль

Запретить отключение нельзя. Датчик работает в браузере посетителя, а это недоверенная среда:
код, который контролирует страницу, может вырезать любой другой код. В «Формальной модели» и
«Разборе кода» это ограничение уже названо.

Поэтому задача ставится так: **отключение не должно проходить незаметно**. Тишина датчика
сама становится находкой, как новый скрипт или утечка.

## Кто и как отключает

| Кто | Как | Чем опасно |
|---|---|---|
| Скрипт злоумышленника | Удаляет тег датчика, подменяет `fetch` / `XMLHttpRequest` раньше датчика, берёт «чистый» `fetch` из нового `iframe` | Скиммер работает, а датчик молчит или не видит отправку |
| Посетитель | Блокировщик рекламы, расширения | Часть посещений без контроля; не атака, но пробел |
| Владелец или его разработчик | Убрал строку при обновлении темы или CMS | Сайт без защиты, а владелец думает, что защищён |

## Пять слоёв

### 1. Датчик стоит первым и проверяет сам себя
*Есть частично*: датчик сохраняет оригинальные `fetch`, `XMLHttpRequest`, `sendBeacon` и ставит обёртки.

Добавить:
- синхронную загрузку первым тегом в `<head>`, до любых скриптов, чтобы никто не успел подменить функции раньше;
- периодическую проверку, что `window.fetch` и остальные всё ещё наши обёртки. Если их подменили, это находка `SENSOR_TAMPERED` с риском как у подмены скрипта;
- **сверку двух каналов внутри страницы.** `PerformanceObserver` видит каждый сетевой запрос средствами браузера, обёртка — только запросы через `fetch`/XHR. Если запрос есть в Resource Timing, а обёртка его не видела, значит её обошли (например, через `fetch` из нового `iframe`). Это находка `SENSOR_BYPASS`.

### 2. Тишина — это тревога
*Есть частично*: heartbeat раз в 10 секунд, кабинет показывает «молчит N мин».

Проблема: heartbeat доказывает, что датчик жив *хоть где-то*. Если его вырезали только на `/checkout`,
heartbeat с других страниц идёт дальше. Нужно **покрытие**:

- сервер сайта считает просмотры страниц сам: плагин CMS, middleware или лог nginx;
- Argus сравнивает по каждой странице: отдано N просмотров, датчик отчитался о M;
- покрытие `M / N` ниже порога (например, 90 %) — находка, в кабинете сразу видно, на какой странице пробел;
- надёжнее всего, если сервер даёт каждой загрузке страницы **разовый код** (nonce в атрибуте тега), а датчик возвращает его в первом пакете. Код, который не вернулся, — точная загрузка страницы без датчика.

### 3. Второй канал в браузере, который не убрать из JS
Заголовок ответа `Content-Security-Policy-Report-Only` с адресом отчётов Argus (`report-to`).
О каждом скрипте с непредусмотренного домена браузер сообщает сам, без JavaScript.
Заголовок выставляет сервер сайта, и внедрённый скрипт снять его не может, даже если вырезал датчик.

CSP не заменяет датчик: не видит подмену содержимого на разрешённом домене и потоки ПДн
(в «Разборе кода» это уже объяснено). Зато служит независимым свидетелем.

### 4. Внешняя проверка
*Описана в модели как «второй канал»*.

Сервер Argus по расписанию открывает страницы сайта чистым headless-браузером и проверяет:
тег датчика на месте, хеши скриптов совпадают с эталоном, новых скриптов и получателей нет.
Работает даже без посетителей и ловит случай «владелец убрал строку».

### 5. Меньше поводов для блокировщиков
Датчик отдаётся с адреса самого сайта (`site.ru/argus/s.js` или поддомен `argus.site.ru`),
а не со стороннего домена: блокировщики режут его реже. Долю посещений с работающим датчиком
показываем открыто, это то же покрытие из слоя 2.

## Что показывает кабинет

- **Список сайтов** (`site/cabinet.html`): строка датчика в каждой карточке — «на связи · 4 с назад · покрытие 99 %» или жёлтым «работает на 64 % просмотров · без датчика: /checkout». Слабое покрытие переводит сайт в «Проверьте».
- **Пульт сайта** (`site/dashboard.html`, обзор): блок «Датчик» — связь, покрытие просмотров, страницы без датчика, внешняя проверка. В шапке пилюля «датчик на связи / работает не везде / молчит».

В демо покрытие условное: в датчике и на сервере его пока нет.

## Порядок работ

1. Сервер: счётчик просмотров по страницам + покрытие в `GET /api/sites/:id/summary` (`stats.coverage`, `stats.coverageGap`). Кабинет уже читает эти поля.
2. Датчик: проверка обёрток и сверка с `PerformanceObserver` → находки `SENSOR_TAMPERED`, `SENSOR_BYPASS`.
3. Приём CSP-отчётов: `POST /csp-report` → находки как у `NEW_SCRIPT`.
4. Внешняя проверка по расписанию на Playwright (стенд и `scenarios/run.js` уже есть).
5. Nonce на загрузку страницы — когда появится плагин для CMS.

Для ВКР: пункты 1–2 можно сделать и проверить на стенде новыми сценариями `?attack=sensor-cut`
(вырезать датчик на одной странице) и `?attack=fetch-iframe` (обойти обёртку через iframe).
